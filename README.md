# Immune Cell Clinical Trial Analysis

Immune cell population analysis on clinical trial data, with an interactive Streamlit dashboard.

**Dashboard:** [jamesvdinh-teiko-clinical-trial-analysis.streamlit.app](https://jamesvdinh-teiko-clinical-trial-analysis.streamlit.app)

---

## Quickstart

```bash
make setup      # install dependencies
make pipeline   # initialize database and generate outputs
make dashboard  # start the local dashboard at http://localhost:8501
```

Tested with Python 3.10+. No virtual environment required — dependencies install to the active Python environment.

### Design rationale

The dashboard code is split into three layers:

- **`src/analysis.py`** owns all data access and computation — SQL queries, frequency calculation, Mann-Whitney U tests, and table styling. It is the only file that touches the database.
- **`src/charts.py`** owns all Plotly figure construction. It imports constants from `analysis.py` but has no database or Streamlit dependency.
- **`app.py`** is pure layout — it calls the two modules above and arranges the results using `st.*` calls. It contains no business logic.
- **`scripts/run_analysis.py`** is a Streamlit-free clone of the analysis layer used by `make pipeline` to write static output files.

SQL queries live as `.sql` files in `sql/` so they can be read, tested, and version-controlled independently of the Python code.

## Database Schema

### Current design

A single table stores all observations:

```sql
CREATE TABLE clinical_trial_observations (
    sample_id                   TEXT PRIMARY KEY,
    project_id                  TEXT NOT NULL,
    subject_id                  TEXT NOT NULL,
    condition                   TEXT NOT NULL,   -- e.g. melanoma, carcinoma
    age                         INTEGER NOT NULL,
    sex                         TEXT NOT NULL,
    treatment                   TEXT NOT NULL,   -- e.g. miraclib, phauximab
    response                    TEXT,            -- 'yes' | 'no' | NULL (healthy)
    sample_type                 TEXT NOT NULL,   -- e.g. PBMC, WB
    time_from_treatment_start   INTEGER NOT NULL,
    b_cell                      INTEGER NOT NULL,
    cd8_t_cell                  INTEGER NOT NULL,
    cd4_t_cell                  INTEGER NOT NULL,
    nk_cell                     INTEGER NOT NULL,
    monocyte                    INTEGER NOT NULL
)
```

The schema is intentionally flat for this dataset size. `sample_id` is the natural primary key (each row is one sample draw). Cell counts are stored as raw integers; relative frequencies are computed at query time to avoid storing derived data.

### Scaling considerations

At hundreds of projects and thousands of samples the flat table starts to show strain in three ways:

1. **Repeated subject/project metadata.** Every row duplicates `project_id`, `condition`, `age`, `sex`, and `treatment`. Normalising into separate `projects` and `subjects` tables eliminates this redundancy and makes subject-level queries (e.g. "all samples for subject X") cheaper.

2. **Fixed cell-type columns.** Adding a new immune population today requires a schema migration. A long (unpivoted) `cell_measurements (sample_id, population, count)` table accommodates any number of populations without schema changes and is better suited to analytical queries that aggregate across populations.

3. **Query performance.** Analytics always filter on `treatment`, `condition`, `sample_type`, `response`, and `time_from_treatment_start`. Composite indexes on those columns (or partitioning by `project_id` in a warehouse) keep scans fast as row counts grow.

A normalised target schema for scale:

```text
projects  (project_id PK, ...)
subjects  (subject_id PK, project_id FK, condition, age, sex, treatment, response)
samples   (sample_id PK, subject_id FK, sample_type, time_from_treatment_start)
cell_measurements (sample_id FK, population TEXT, count INTEGER)
```

For read-heavy analytics workloads (many concurrent dashboard users, large cohorts) a columnar store such as DuckDB or BigQuery would be preferable to SQLite, since they vectorise aggregations and scans across millions of rows with no index tuning required.
